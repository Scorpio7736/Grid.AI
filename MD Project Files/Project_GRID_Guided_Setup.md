# Guided setup and health diagnostics (6.34)

Local onboarding implementation updated 2026-11-16. Physical multi-device acceptance remains open; see the limits below.

## Use

- `Grid.Terminal.exe --setup [absolute-new-profile.json]`: review PC versus Flash deployment, an existing local world-directory choice, hardware estimates and off/Lite inference. Only `save` writes a new preference file; existing profiles are never overwritten. Saving alone does not open or move a world. A final explicit `launch` continues into the selected world's existing masked credential setup/login. Bare interactive first launches offer setup before creating the default world; scripted/explicit-world launches retain their existing behavior.
- `Grid.Terminal.exe --configured <profile.json>`: explicitly launch the selected world and inference preferences. No other launch flags are accepted. Existing local identity/login remains required. Profiles contain no secrets or grants.
- `Grid.Terminal.exe --doctor [profile.json]`: read-only hardware, managed-asset and capability guidance for the selected storage location. It verifies pinned model hashes when Lite resources are sufficient; it does not start inference, record audio, capture screens, change permissions or repair files.
- `Grid.Terminal.exe --doctor-check <profile.json>`: explicit active checks with a five-minute total deadline and Ctrl+C cancellation. Tests a unique delete-on-close storage file, offline voice inventory, synthetic-image OCR, current-session window metadata and a real pinned local-model text reply. Reports each failure independently with repair guidance and returns nonzero on failure. It never opens the world, captures a desktop, records audio, grants a capability or downloads assets. Its private inference process is disposed; runtime cache/log files may remain.
- Rollback: launch normally for the original default world, or select an earlier profile. To edit preferences, create a new profile. This does not restore/delete world data.

PC profiles require an absolute local database path with an existing parent; network paths, alternate streams and reparse ancestors are refused. Flash profiles require an existing portable package and use package-relative `data/world.db`. A different machine requires setup again; no grants move with a profile.

Lite uses the pinned installed Qwen3 4B model with reduced context and CPU requests, requiring measured Windows x64 compatibility, 8 GB available RAM and 256 MB free reserve. These are conservative eligibility estimates, not measured performance or full installation-space estimates. Standard and Performance remain unavailable pending model/device acceptance. GPU details use the existing bounded optional driver collector and may be unknown.

In a source clone, setup offers `keep` (default), `offline` (verified local runtime/NuGet cache) or `download` (explicit online installation). It displays the exact installer, network mode, existing runtime/app/data/staging inventory, free space and a conservative 20 GB additional staging/build budget. Only the exact confirmation `install` invokes `Setup-GridClone.ps1`; offline failure never retries online. Space is rechecked after review. Existing world and runtime files are preserved; incomplete runtimes require the separate explicit repair action described in the [clone installation reference](Project_GRID_Fresh_Clone_Installation.md). The wizard refuses to rebuild `.grid-app` while running from that output directory; close it and run the displayed installer from PowerShell, then reopen setup. Installation is not an atomic rollback of application binaries; the installer readiness gate remains authoritative.

Portable users provision before transfer using `Prepare-GridRuntime.ps1` or a complete package. Flash setup never starts a clone installer. No setup path falls back to global Ollama or cloud inference. Model hashes do not authenticate arbitrary runtime binaries. Existing disable environment settings remain authoritative.

Identity remains in the selected world, never in the launch profile. New worlds use the existing masked username/password flow; existing worlds require their current owner. `credentials` after login rotates credentials and invalidates old sessions. The setup and credential screens explain that there is no password-reset bypass/recovery code; users retain their password in their own password manager. World backup recovery is a separate explicit `--recover --world <path>` action that rolls back world changes, not a forgotten password. Setup displays that exact selected-world path without executing recovery.

Optional capabilities default to no grants. The optional review explains Windows privacy controls separately from agent authorization, offline versus online provisioning, `voice cancel`/`voice mute on`/Esc, `screen stop`, workspace/storage registration disable and `device revoke`. Rerun setup with a new profile for later edits; selecting the earlier profile rolls back preferences without deleting or migrating worlds.
