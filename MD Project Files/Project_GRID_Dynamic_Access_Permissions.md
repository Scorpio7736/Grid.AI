# Grid.AI Dynamic Access and Remembered Permissions

Implemented 2026-11-21 as a pre-Phase-7 conversational foundation.

## Governing workflow

MCP follows this order for every request:

1. Determine the user's intended outcome.
2. Determine a viable route to that outcome.
3. Identify the access path required by that route.
4. Reuse a valid saved grant or ask the user for the required permission.
5. Execute only through a registered, host-validated provider.
6. Interpret the provider's evidence into a natural answer.

Questions and answers are generated by the agent model for the current conversation. They are not phrase-specific templates. GRID constrains only the machine-readable route, registered access path, risk, scope and duration. An invented path is refused rather than translated to the nearest capability.

## Plain source code versus file creation (follow-up)

The operator's request to **write, generate or draft an example of C#, Python, Java or other source code in conversation** is treated as an ordinary answer when no destination, project, repository, or file target is named. Explicit file creation, changes within a registered workspace, and host compilation still follow the existing authenticated, review-and-approval flow. A plain code answer does not authorize file writes and cannot grant host access. The route deliberately excludes path/destination terms rather than guessing where to save the generated text.

MCP's generated coding examples are **not compiled or tested by chat**. A 2026-11-21 live BST example answered normally yet contained a non-compiling `var parent = null`, a non-terminating insertion loop and contradictory testing claims. The persona now explicitly asks the model to review type inference, loop termination, branch coverage, completeness and evidence-backed verification language. These are model-quality instructions, **not a compiler or quality guarantee**; only host-authorized compilation/tests and their verified receipts can establish that generated code works. Live retesting of this prompt change is still open.

## Access paths, not individual facts

Permissions apply to bounded kinds of access. They are not separate permissions for the clock, Bluetooth, or another individual value. Implemented paths are `host.system.read`, a bounded read-only system-information path, and `host.system.write`, a High-risk bounded system-setting path. MCP can use the read path to answer different current-host questions, including local date/time and present Bluetooth inventory. The write path accepts only registered typed operations; model text can plan parameters but cannot become an arbitrary command. Registered clock mutations are a relative adjustment of at most 24 hours, an exact ISO calendar date, and a calendar day within the host's current month/year while preserving local time. Windows displays its own UAC confirmation before the elevated helper can apply one.

Future filesystem and application integrations must follow the same rule: request access to the necessary directory boundary or application boundary, then let the agent reason within that authorized path. Do not add one permission or canned dialogue per directory, application, question or fact.

## Risk sections

| Risk | Intended access | Current rule |
|---|---|---|
| Normal | Read and observe | May be granted once, for the session, or always. The implemented system-information path is Normal. |
| Medium | Create, write and update | The durable tier exists. Existing file tools still require a complete preview, exact target validation and explicit apply; a standing access grant does not approve content. Broader dynamic-path integration remains planned. |
| High | Delete and destructive actions | The typed system-setting path is implemented for bounded relative or calendar-date Windows clock changes and requires permission plus Windows UAC. Existing deletion/destructive workflows retain high-risk acknowledgement and recoverability rules; a standing access grant never silently approves a deletion. Broader dynamic-path integration remains planned. |

Risk and approval are separate. A saved permission opens an access boundary; it does not prove execution, approve a task, accept generated content, grant Windows elevation or bypass an exact change review.

## Duration and memory

- Plain consent defaults to **Once** and is consumed by the single operation.
- “Only this time” creates a **Once** grant.
- “For this session” creates a **Session** grant, valid only for the current authenticated terminal session.
- “You can always do this” or “remember this permission” creates an **Always** grant saved in the world and reused on later matching requests.
- `permissions` lists grants by Normal, Medium and High risk, including duration and state.
- `permissions revoke <id>` revokes a saved grant. Future matching requests must ask again.

Schema v28 records the durable permission contract. One-time grants remain as consumed audit records. Session grants are retained but inactive outside their issuing session. Always grants survive save/reload until revoked.

## Plain answers versus host access (2026-11-21 follow-up)

A user's request for an algorithm explanation, source-code sample, or general programming guidance is **conversation text**, not a request to compile/run code or read the user's PC. The terminal now routes clear conceptual/advice prompts directly to the ordinary MCP text inference path, avoiding an unnecessary structured permission decision. MCP's local instructions explicitly permit writing C# examples without host access. Requested detailed answers are no longer subject to the ordinary-chat 100-word guidance, and MCP's initial output ceiling is 1,024 tokens; performance and full-answer quality require further physical testing.

**Security boundary:** Only the explicitly requested structured host access route can produce a pending host-access proposal. A model-generated route JSON envelope in a plain chat is untrusted; a valid `Conversation` envelope is unwrapped, while an `Access` envelope or invalid routing JSON is retried once as plain text under the same authorization/queue checks and cannot create permission state. Host/system questions retain the explicit structured access path; file edits and tasks retain their existing separate reviewed workflows. Added tests cover ordinary code explanations, injected route JSON, and structured date access. **Regression tests and live acceptance pending user execution**; no claim of verified execution after these changes.

## Acceptance and limitations

The bundled Qwen3 4B passed a real date → consent → Bluetooth → consent replay, then correctly converted the reported natural request to change “today” to the 22nd into a High-risk permission question without asking for time zone, format or commands. The acceptance stopped at the permission boundary and did not change the test PC clock. Access-route validation rejects refusal prose and missing-information questions as permission state; a model-generated consent imperative may receive punctuation-only normalization.

The validated typed mutation is now bound to the pending permission request. Consent executes that exact object instead of asking the model to recreate a plan after approval, preventing plan drift and the misleading file-preview fallback reported for “go ahead.” The consent interpreter retries only the typed Once/Session/Always/Cancel/Unclear contract and validates that host-access replies cannot become preview actions. A non-mutating injected host adapter verified the full `+60 seconds` request → permission → “go ahead” → exact bound execution → conversational receipt flow; the one-time grant was consumed and no second planning call occurred. Final verification passed all **1,654 solution tests** (14 Core, 163 Simulation, 109 Persistence, 1,368 Terminal), zero failed/skipped. Actual clock mutation remains a manual UAC acceptance test.

Normal system-information access is verified end to end. High-risk system-write execution is implemented for the typed Windows clock operations but remains manual acceptance because its real test necessarily changes the host clock and invokes UAC. Medium remains a durable policy foundation. Broader dynamic filesystem/application paths remain planned, and existing reviewed file/task/delete services remain authoritative.
